# 2. 데이터베이스 안의 스키마와 테이블 관찰

## 2-1. 스키마 조회 결과

실행한 SQL:

```sql
SELECT schema_name
FROM information_schema.schemata
ORDER BY schema_name;
```

관찰한 스키마 이름 중 3개 이내를 적습니다.

```text
1. information_schema
2. practice
3. public
```

### `public`은 무엇인가요?

```text
나의 설명: public은 PostgreSQL 데이터베이스 안에 기본적으로 제공되는 스키마이다. SQL에서 스키마 이름을 따로 지정하지 않으면 객체가 public 스키마에 생성되거나 조회될 수 있다.
```

### 데이터베이스와 스키마는 같은 것인가요?

```text
나의 설명: 아니다. 데이터베이스는 여러 데이터와 객체를 포함하는 상위 공간이고, 스키마는 하나의 데이터베이스 안에서 테이블 등의 객체를 구분하고 정리하는 하위 공간이다.
```

## 2-2. 현재 보이는 테이블 조회

```sql
SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_type = 'BASE TABLE'
  AND table_schema NOT IN ('pg_catalog', 'information_schema')
ORDER BY table_schema, table_name;
```

```text
조회된 사용자 테이블 수 또는 눈에 띈 테이블: 사용자 테이블은 1개이며, practice 스키마의 members 테이블이 조회되었다.

아직 테이블이 거의 없어도 괜찮은 이유: 현재 데이터베이스에 사용자가 직접 만든 일반 테이블만 조회되기 때문이다. 필요한 테이블은 이후 실습에서 새로 만들 수 있으므로 테이블이 적게 조회되어도 실행 오류는 아니다.
```

## 2-3. 관찰 정리

```text
PostgreSQL 서버 안에는 여러 데이터베이스가 있을 수 있다.
한 데이터베이스 안에는 여러 스키마가 있을 수 있다.
스키마 안에는 테이블과 같은 데이터베이스 객체가 존재한다.
```

# 4. 테이블과 조회 결과는 다르다

## 4-1. 원본 테이블 행 수

```text
ch02_students 전체 행 수: 3
```

## 4-2. 일부 열만 조회

실행 SQL:

```sql
SELECT name, major
FROM ch02_students
ORDER BY id;
```

```text
원본 테이블의 열 수와 조회 결과의 열 수가 다른 이유: 원본 ch02_students 테이블에는 id, student_number, name, major의 열 4개가 있지만, SELECT 문에서 name과 major만 지정했기 때문에 조회 결과에는 열 2개만 나타났다. 
```

## 4-3. 조건을 적용한 조회

실행 SQL:

```sql
SELECT id, student_number, name, major
FROM ch02_students
WHERE major = '컴퓨터공학'
ORDER BY id;
```

```text
원본 테이블 행 수: 3
조회 결과 행 수: 1
원본 테이블의 데이터가 삭제된 것인가?: 아니다.
그렇게 판단한 이유: WHERE 조건은 원본 테이블에서 조건에 맞는 행만 조회 결과에 보여 줄 뿐이다. major가 컴퓨터공학인 김민지 학생만 표시되었지만, 원본 테이블에는 학생 3명의 데이터가 그대로 저장되어 있다.
```

## 4-4. 정렬 결과 비교

```sql
SELECT id, name
FROM ch02_students
ORDER BY name ASC;

SELECT id, name
FROM ch02_students
ORDER BY name DESC;
```

```text
ASC 결과의 첫 학생: 김민지
DESC 결과의 첫 학생: 이준호

이 실험을 통해 ORDER BY에 대해 알게 된 점: ORDER BY에서 ASC를 사용하면 이름이 오름차순으로 정렬되고, DESC를 사용하면 그 반대 순서로 정렬된다. 또한 ORDER BY를 명시하지 않은 조회 결과의 행 순서는 항상 보장된다고 가정하면 안 된다.
```

# 5. PK와 FK를 실제로 관찰

## 5-1. 정상 데이터의 관계 읽기

다음 SQL 결과를 보고 작성합니다.

```sql
SELECT
    e.id AS enrollment_id,
    s.name AS student_name,
    c.title AS course_title,
    e.status
FROM ch02_enrollments AS e
JOIN ch02_students AS s
    ON s.id = e.student_id
JOIN ch02_courses AS c
    ON c.id = e.course_id
ORDER BY e.id;
```

```text
한 행이 의미하는 것: 학생 한 명이 강의 한 개를 신청한 수강신청 한 건과 그 현재 상태를 의미한다.

같은 student_id가 여러 enrollment 행에서 반복될 수 있는 이유: 학생 한 명이 여러 강의를 신청할 수 있으므로 같은 학생을 참조하는 student_id가 여러 수강신청 행에서 반복될 수 있다.

같은 course_id가 여러 enrollment 행에서 반복될 수 있는 이유: 강의 한 개를 여러 학생이 신청할 수 있으므로 같은 강의를 참조하는 course_id가 여러 수강신청 행에서 반복될 수 있다.
```

## 5-2. 기본키 중복 오류 관찰

중복 PK 입력을 시도한 결과:

```text
실행 성공 / 실패: 실패

오류 메시지에서 확인한 핵심 단어: SQL Error [23505], 중복된 키 값, ch02_students_pkey, (id)=(1) 키가 이미 있습니다.

왜 실패했다고 생각하는가: ch02_students 테이블에서 id는 각 학생 행을 고유하게 구분하는 기본키이다. 기존에 id가 1인 행이 있으므로 같은 id를 가진 새로운 행의 저장을 PostgreSQL이 거부했다.
```

## 5-3. 존재하지 않는 학생을 참조하는 FK 오류 관찰

존재하지 않는 `student_id`를 사용한 수강신청 입력 결과:

```text
실행 성공 / 실패: 실패
오류 메시지에서 확인한 핵심 단어: SQL Error [23503]이 발생했으며, student_id 값 999가 ch02_students 테이블에 존재하지 않아 외래키 제약조건을 위반했다.
왜 실패했다고 생각하는가: ch02_enrollments.student_id는 ch02_students.id를 참조한다. 학생 테이블에 ID가 999인 학생이 없으므로, 존재하지 않는 학생의 수강신청이 저장되지 않도록 PostgreSQL이 입력을 거부했다.
```

## 5-4. PK와 FK의 차이 정리

```text
PK는 한 테이블 안에서 각각의 행을 중복 없이 고유하게 구분하기 위한 키이다.

FK는 다른 테이블의 PK를 참조하여 두 테이블 사이의 관계를 표현하고, 존재하지 않는 데이터를 참조하지 못하게 하기 위한 키이다.

FK 값이 여러 행에서 반복될 수 있는 이유는 학생 한 명이 여러 강의를 신청하거나 강의 하나에 여러 학생이 신청할 수 있기 때문이며, 하나의 학생 또는 강의를 참조하는 FK 값이 여러 수강신청 행에서 반복될 수 있기 때문이다.
```

# 6. 관계와 카디널리티를 자연어로 설명

현재 임시 데이터 기준으로 작성합니다.

```text
학생 한 명은 여러 수강신청을 가질 수 있는가?: 그렇다. 현재 데이터에서도 김민지 학생은 다른 두 강의에 대한 수강신청을 가지고 있다.

강의 한 개는 여러 수강신청을 가질 수 있는가?: 그렇다. 현재 데이터에서도 데이터베이스 입문 강의는 김민지 학생과 이준호 학생의 수강신청과 연결되어 있다.

수강신청 한 건은 학생 몇 명을 참조하는가?: 학생 한 명을 참조한다.

수강신청 한 건은 강의 몇 개를 참조하는가?: 강의 한 개를 참조한다.
```

아래 구조를 완성합니다.

```text
students 1 ── N enrollments N ── 1 courses
```

### 학생과 강의가 N:M 관계라고 볼 수 있는 이유

```text
나의 설명: 학생 한 명은 여러 강의를 수강할 수 있고, 강의 한 개에도 여러 학생이 참여할 수 있기 때문에 학생과 강의는 N:M 관계이다. 이 관계를 직접 두 테이블에 저장하지 않고, enrollments 연결 테이블에 학생 ID와 강의 ID를 저장하여 두 개의 1:N 관계로 표현한다.
```

> 아직 0개 허용 여부, 필수 관계, 삭제 정책까지 확정하지 않습니다. 그런 규칙은 Chapter 05~06에서 다룹니다.

# 7. AI가 만든 테이블 구조 직접 검토

## 7-1. AI에게 묻기 전에 내가 먼저 찾은 문제

다음 구조를 보고 최소 4개를 적습니다.

```sql
CREATE TABLE student_courses (
    student_name VARCHAR(50),
    student_email VARCHAR(100),
    course_title VARCHAR(100),
    instructor_name VARCHAR(50)
);
```

```text
문제 1. 행을 구분하는 PK가 존재하지 않는다.
문제 2. 학생의 정보 여러 행 중 일부 정보가 수정되면 학생의 이름과 이메일이 달라지는 문제가 생긴다.
문제 3. 강의 제목과 교수자 이름이 연결되어있지 않아 하나가 바뀌어도 다른 행이 바뀌지 않는다.
```

## 9-1. 사용한 프롬프트

```text

현재 생각한 테이블은 다음과 같습니다.

- 한 행: 가맹점 한 곳
- PK 후보: store_id

- 업무 식별자 후보: owner_code

3. menus
- 한 행: 메뉴 한 개
- PK 후보: menu_id
- 업무 식별자 후보: menu_code

4. orders
- 한 행: 특정 가맹점에서 발생한 주문 한 건
- PK 후보: order_id
- 업무 식별자 후보: order_number
```

# 10. 최종 개념 정리

아래 문장을 본인의 말로 완성합니다.

```text
PostgreSQL은 데이터를 테이블 형태로 저장하고 관계와 제약조건을 관리하며 SQL을 처리하는 관계형 DBMS이다.

DBeaver 또는 psql은 PostgreSQL에 접속하여 SQL을 작성, 실행하고 그 결과를 확인하는 클라이언트 도구이다.

데이터베이스와 스키마의 차이는 데이터베이스가 여러 데이터와 객체를 담는 큰 단위이고, 스키마는 하나의 데이터베이스 안에서 테이블 등의 객체를 구분하고 관리하는 이름 공간이라는 점이다.

테이블 한 행은 해당 테이블이 표현하는 대상이나 사건 한 건을 의미한다.

조회 결과가 원본 테이블과 다른 이유는 SQL이 원본에서 필요한 행과 열을 골라 결과로 보여주기 때문이다. 일부만 조회하거나 정렬해도 원본 데이터는 바뀌지 않는다.

내부 식별자와 업무 식별자의 차이는 내부 식별자는 데이터베이스에서 행을 안정적으로 구분하고 참조하기 위한 값이고, 업무 식별자는 학번이나 주문 번호처럼 실제 업무에서 대상을 구분하기 위해 사용하는 값이라는 점이다.

PK는 자신의 테이블에서 각 행을 중복 없이 고유하게 구분하며 NULL을 허용하지 않는 열 또는 열의 조합이다.

FK는 다른 테이블이나 같은 테이블의 키를 참조하는 열 또는 열의 조합이다. FK 제약조건은 존재하지 않는 값을 참조하는 입력을 막는다.
```
